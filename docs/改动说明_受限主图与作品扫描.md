## 一、38 张版权保留主图：从「手工一次」改成「导出阶段自动」

### 1.1 为什么不能只跑一次 `npm run strip:restricted`

原设计是：发布前手工跑一次 `npm run strip:restricted`，把 38 张图删掉。

**但这在同步链路里是错的。** 导出脚本会「清空重建」发布包——手工删掉的 38 张，
下一次导出时会被原样拷回来。于是：

> 手工跑一次 → 导出 → 38 张又回来了 → 再手工跑一次 → ……

发布结果取决于「上次有没有人记得跑过」，不可重复、不可复现。这在「素材库持续增长、
每次发布都要能自动验收」的目标下是不能接受的。

### 1.2 采取的做法：把剔除嵌进导出流程

`04_工具\导出开源包.mjs` 新增 **2.6 步「版权保留主图剔除」**，位置很关键：

```
2. 参考图拷贝  →  2.5 第三方素材剔除  →  2.6 版权保留主图剔除  →  3 工具脚本
                                                                    →  4 服务端
                                                                    →  5 生成图鉴 HTML
```

**必须在第 5 步生成图鉴之前**，否则图鉴里会留下指向已删图片的引用（破图）。

这一步做三件事：

1. 读 `04_工具\_抓取缓存\atlas-effects.json`，用 `授权分类.mjs` 的 `classifyCredit()`
   重新判读每张主图，挑出 `redistributable === false` 的 38 条
2. 删除 `assets/风格参考图/风格图鉴_<slug>.webp`
3. 清空三库中这些条目的 `refs`，并打上 `refsStripped: true` + `refsStrippedReason`

**条目文本、提示词、来源链接、逐条署名全部保留**——只是不含图片文件。

实测：删除 **38 张** / 清空 **44 处引用**。44 > 38 是因为有 6 个 atlas 效果同时出现在
风格库和光影库（`atlas-anamorphic-lens-flare` 与 `atlas-light-anamorphic-lens-flare`
共用同一张主图文件），两处引用都要清。

## 三、克隆者扫描**他自己的**作品

### 3.1 新增 `tools/扫描我的作品.mjs`

通用扫描器，零第三方依赖，**只读**——不移动、不删除、不修改被扫描目录里的任何文件。

```bash
npm run scan -- "D:/你的作品目录"
```

- 扫描根下的**一级子目录**各算一个作品
- 自动跳过 `node_modules` / `.git` / `.venv` / `dist` / `coverage` / `.mh` 等依赖与运行时目录
- 产物：`我的作品/{index,works,summary}.json`
- 有 `ffprobe` 就顺带探测视频时长、分辨率、帧率、编码；没有就只记文件元数据

实测：扫 `02_素材\图片库` → 3518 个文件 / 310.71 MB / 5 个作品 / 0.1 秒。

### 3.2 新增「我的作品」页面与接口

| 接口 | 作用 |
|---|---|
| `GET /myworks` | 作品浏览器（搜索 + 按作品/类型筛选 + 图片/视频/音频预览） |
| `GET /api/myworks` | 作品清单与统计；**没扫描过时优雅降级**（`scanned:false` + 扫描指引），不报错 |
| `GET /api/myassets?q=&work=&cat=&limit=&offset=` | 我的素材检索 |
| `GET /api/myasset?id=` | 单个素材详情 |
| `GET /media/<素材id>` | 媒体直出 |

**安全模型**与本地工作台同一套：按 **id** 查表拿绝对路径，**绝不接受裸路径**；
再校验该路径仍在扫描根之下。实测 3 种穿越尝试全部 404：

```
/media/..%2f..%2fpackage.json                → 404
/media/notexist                               → 404
/media/%2e%2e%2f%2e%2e%2fdata%2f风格库.json    → 404
```

媒体直出支持 **Range** 请求，视频/音频可以拖动进度条。

### 3.3 与参考库互不干扰

- 参考库（三库 + 参考图）是**仓库的一部分**，随仓库分发
- 「我的作品」是**用户本机的索引**，在 `.gitignore` 里
- 重新导出会**保留** `我的作品/`（与 `.git` 一样），不会把用户的扫描结果一起删掉
- 但泄露扫描与变更快照都**跳过**它——它不是包内容

## 四、个人内容绝不入库：三道防线

| 防线 | 机制 | 失效后果 |
|---|---|---|
| ① 目录隔离 | `我的作品/` 写进模板 `.gitignore` | git 根本不会看到它 |
| ② 显式排除 | 导出脚本、泄露扫描、变更快照、冒烟测试的哈希遍历全部跳过 `我的作品/` | 不会被当成包内容 |
| ③ 硬断言 | `npm run verify` 检查 `git ls-files -- 我的作品` **必须为空**，且 `.gitignore` 必须含该规则 | 有人误改 .gitignore 或 `git add -f` → verify 立刻失败，发布卡住 |

实测：`git ls-files -- 我的作品` → **0 个文件**；
`git check-ignore -v 我的作品/index.json` → 命中 `.gitignore:9`。
